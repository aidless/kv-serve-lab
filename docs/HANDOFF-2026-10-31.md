## 2. 三条红测试对应的是真缺陷（已读源码确认，不是测试写错）

### 缺陷 A：`schedsim` 到达判定用固定步号换算

`kv_serve_lab/schedsim/__init__.py:406-407`：

```python
base = self._base_step() if self._base_step() > 0 else 1.0
return int(math.ceil(arrival_sec / base - 1e-9))
```

等时模型下成立，但**成本模型**（`step_overhead + prefill_tokens×t_prefill_token + decode_reqs×t_decode_token`）下每步墙钟长度不同，第 k 步的真实时刻不再是 `k × base`。后果是到达判定可能过早（时间倒流）或过晚。

复现：`max_num_batched_tokens=64, max_num_seqs=4, step_overhead=0.05, t_prefill_token=0.005`，请求 0.10s 到达 → step 0 跑 20 个 prefill token 耗时 `0.05+20×0.005=0.15`，step 1 起点 0.15 ≥ 0.10，**应进 step 1**；实测 `assert 2 == 1`（进了 step 2，晚一步）。

修法：判据换成墙钟比较——某步起点 `now >= arrival_sec` 才接纳。

### 缺陷 B：空闲跳转按固定步长推

同文件 `:316`：`gap = (next_step - step) * self._base_step()`。

复现：单请求、`step_overhead=0.02, t_prefill_token=0.01`、8 token prompt、0.37s 到达 → 首 token 应在 `0.37+0.10=0.47`；实测 `0.48`（`assert 0.48 == 0.47 ± 4.7e-07`）。

### 缺陷 C：`bench` 让文本覆盖服务端 usage（口径反了）

`kv_serve_lab/bench/__init__.py:179-193`：先读 `usage.completion_tokens` 算 `n_tokens`，随后 `if text: ... if token_counter is None: raise BenchError` —— **无 tokenizer 时直接抛错，即使服务端已给权威 usage**。

复现：单个 chunk `{"choices":[{"text":"aa bb"}],"usage":{"completion_tokens":3}}`，`trace_from_payloads("r", 0.0, payloads)`（故意不给 tokenizer）→ 期望 `output_len == 3`，实测抛 `BenchError: r: chunk carries text but token_counter is None`。

**规则应是「有 usage 就以 usage 为准，文本只在没有 usage 时参与计数」**——与 `ttftkit` 的既有口径一致（该仓库已把这条写成硬规则）。

### 7.2 `ERR conservation`：构造函数只填 `free_` 不建 `free_pos_`（本会话定位并修复）

**症状**（23:14，seed=3/20261031 两条红）：前 19 行两边逐字节一致，
第 20 行 `acquire h4` → Python `OK 3`，C++ `ERR conservation`。

**取到的证据**：acquire 失败后紧接着 `audit`，C++ 自报

```
$ ./cpp/build/kvbm 4 2 <<< 前20行 + acquire h4 + audit
ERR conservation
OK total=4 used=1 free=4 cached=1      ← 4 个块，却 used=1 且 free=4
```

块被同时算进两个分区。加 `KVBM_DEBUG=1` 看第一个 `alloc` 的内部态：

```
[alloc pop 0] free=0,1,2,3, mapkeys=
```

`free_pos_` 是空的。构造函数（`:87` 原为 `for (...) free_.push_back(i);`）**只 push 队列、没建反查索引**，
而 `free_erase()`（`:363-367`）以 `free_pos_` 为唯一真相，`find` 不到就**静默 return**。
于是 acquire 命中缓存块时该块留在 `free_` 里、又被插进 `in_use_` → `check_conservation()` 判失败。

**修法**（一行，已落盘 `cpp/kv_block_manager.cpp:86-92`）：构造时同步建索引

```cpp
for (long long i = 0; i < num_blocks; ++i) {
    free_.push_back(i);
    free_pos_[i] = std::prev(free_.end());
}
```

**RED→GREEN 验证**（先在 `/tmp/cppdbg` 的独立副本上做，再落到仓库）：

| 阶段 | 结果 |
|---|---|
| RED（未打补丁） | seed=3 第 20 行 `acquire h4`：py `OK 3` / cpp `ERR conservation`；seed=20261031 同样红 |
| GREEN（打补丁后，6 个 seed 全跑） | 1 / 2 / 3 / 7 / 11 / 20261031 → **rc=0，逐行 0 差异**（195–199 行/条，合计约 1188 行） |
| 仓库全量 | `make -C cpp` → `python3 -m pytest` = **231 passed in 21.42s** |

> 这类「只维护一份真相、另一份静默滞后」的 bug 不会被功能测试抓到，只有对拍/守恒检查会抓。
> 建议给 `BlockPool` 加一条 `free_pos_.size() == free_.size()` 的内部断言，把它变成可失败的门。

### 7.3 顺带补的守卫：把「反查表与队列同长」变成可失败的门

7.2 的根因能在 19 个操作里不被发现，是因为 `audit` **不调用** `check_conservation()`
（它只打印计数），所以坏状态可以静默存活到第一次 `acquire` 才炸。

已在 `cpp/kv_block_manager.cpp:132-138` 的 `check_conservation()` 首行加：

```cpp
if (free_pos_.size() != free_.size()) fail(Code::Conservation);  // 反查表与队列必须同长
```

**RED→GREEN 证据**（在 `/tmp/cppdbg` 的两个独立构建上做）：

| 构建 | 输入 | 输出 | 说明 |
|---|---|---|---|
| 坏构造 + **无**守卫（原状态） | `alloc 1` | `OK 0` | 静默通过——正是 bug 能活下来的原因 |
| 坏构造 + 守卫 | `alloc 1` | `ERR conservation` | **门会红**：第一个操作就抓住 |
| 好构造 + 守卫 | `alloc 1` | `OK 0` | **门会绿**：不误杀 |

保守结论：这条守卫把「19 个操作后才炸」提前到「第一个操作就报」，代价是一行比较。
回归后全量 **231 passed**（守卫上线，正常路径无变化）。
